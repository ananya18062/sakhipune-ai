## C. Critical assistance review

**Expedite confirmation for all 22 Priority 1 resources:** CSV-001–014, CSV-016, and CSV-020–023, CSV-042–044. This is a consequence-based queue, not a finding that all 22 are invalid.

- **Emergency numbers (CSV-001–005):** none has a row-specific current official source in the evidence set. Confirm numbers, operator, coverage, hours, cost and routing from official Pune/Maharashtra/national directories before a user-facing “call now” claim.
- **Legal aid and protection services (CSV-006–010, 023):** NALSA E16 provides general statutory context; the Pune DLSA URL returned a page with local DLSA descriptions, but official status/contact/eligibility should be checked. MSLSA current URL failed. WCD E14 does not identify the current Pune Protection Officer. Confirm eligibility and local contact.
- **Healthcare (CSV-011–014):** JSY has direct official NHM guideline evidence at E17, but state-specific eligibility must be accurately conveyed. Sassoon and PMC facility/fee/hour claims lack official local directories. PMMVY portal E13 confirms only portal ownership; the existing CAS URL is inaccessible.
- **Domestic-violence support and shelters (CSV-020–023, 042–044):** no current official Pune OSC or Bharosa Cell listing was retrieved. Do not promise shelter availability, a five-day limit, police referrals, mediation, FIR assistance, or 181/1091 routing without direct sources.
- **Crisis counselling (CSV-016):** Vandrevala number and 24-hour/free/language claims lack a provider-controlled source, so it is included in expedited review even though the general category is Priority 3. iCALL E4 is stronger evidence for CSV-015 and CSV-017’s core TISS service and published hours; that does not validate all issue, confidentiality or language claims.

For unverified critical records, the proposal is to temporarily withhold unsupported record-specific instructions/contacts while expediting review—not to infer that the service does not exist. Any fallback must itself be an independently verified, current official emergency/service directory. No fallback number is proposed in this report.

## D. Filter remediation

### Intended meanings and actual application path

In `backend/app/database/models.py`, `experience_level` means experience **required** (including `fresher` and `any`), `work_mode` means opportunity mode (`remote`, `hybrid`, `on_site`), and `employment_type` is the job type. All three are nullable strings; the code constants document values but do not enforce database constraints or source accuracy. `backend/load_resources.py` maps candidate cells by header, strips them, maps blanks to `None`, and does not validate them.

`filter_utils.py` applies structured job filters as AND conditions; unknown metadata does not match a specific filter. The internship filter applies experience and work mode, but not employment type. `/api/recommend`, which `frontend/js/app.js` currently calls, ranks all resources without these structured filters. Its frontend sends question answers in `preferences`; `questions.js` asks about job type, experience and work preference, but those selections are not the typed structured filter request fields. Therefore the strict metadata is not consistently exposed/applied in the current primary UI/API route. The recommendation risk is primarily false negatives on category routes if guessed metadata excludes a user; inaccurate `any` or type metadata can also cause false positives.

Every status below is **Inconclusive** (equivalent to `Insufficient evidence` in the earlier review). No value is proved false; none has evidence sufficient to use as a factual eligibility/work condition. Keep all values unchanged in source/candidate files while flagged.

## G. Safe recommendation policy — proposed, not implemented

1. **Verified:** allow normal recommendation only for the claims individually verified, with source and review date available. Recheck time-sensitive phone numbers, hours, benefits, eligibility, vacancies and scheme-cycle status on an appropriate schedule.
2. **Partially verified:** do not label the whole record “verified.” Recommend only the explicitly supported, non-misleading portion and display the official source. Keep unsupported amounts, hours, eligibility, local contacts and availability out of user-facing factual assertions until checked. For urgent assistance, require review of the actual contact/routing before displaying it as a call-now action.
3. **Unverified:** do not promote as an established official service or opportunity. Avoid blanket deletion: keep the record in an internal review queue. For critical assistance, expedite manual verification and use a fallback only if that alternative has itself been verified from a current official source; do not substitute an invented or remembered number.
4. **Incorrect:** hold the misleading link/claim combination from recommendations until corrected with direct official evidence. Row CSV-034 has an official portal URL candidate for the URL correction only; its benefit claims remain unverified. CSV-030 has no established replacement policy page.
5. **Inaccessible:** treat as an access limitation, not proof of invalidity. Search for another official department/provider document or directory; until the exact relevant claim is supported, do not say the current page was verified. Do not silently replace the URL with a generic homepage.
6. **Unsupported filter values:** treat as unknown/inactive for eligibility and strict matching until the underlying requirement is established. Do not infer an experience requirement, work mode or employment type from title, location, category or keywords. Keep the original candidate values unchanged during this proposal stage. If an active user preference is collected, distinguish it from resource eligibility and do not exclude services solely because metadata is unknown without a safe, transparent fallback.
7. **Urgent-resource fallback:** maintain a separately reviewed source directory for emergency and crisis access; identify verification date and jurisdiction; if no verified local match is available, say that a local contact could not be confirmed and direct users only to an independently verified official alternative. This proposal does not name or fabricate an alternative.
