## Confirmed mapping and behavior

1. **Candidate-to-model mapping:** The candidate retains the ten model fields in the intended order. The row mapping report points each of these records to its same-numbered original data row (with header counted as row 1). The candidate reconstruction put the three filter values in the dedicated columns; it did not infer them from keyword spillover.
2. **Loader behavior:** `load_resources.py` reads the first 10 named columns using `csv.DictReader`; `_row_to_resource` strips values, stores empty filter strings as `None`, and passes non-empty filter values directly to the three nullable SQLAlchemy columns. It does **not** check values against `EXPERIENCE_LEVELS`, `WORK_MODES`, or `EMPLOYMENT_TYPES`; vocabulary checking performed for the candidate does not establish semantic validity.
3. **Employment endpoint:** `/api/jobs` merges the typed filter request fields into preferences, `get_all_employment_resources` unpacks `experience_filter`, `work_mode_filter` and `employment_type_filter`, then `apply_job_filters` ANDs all active filters. A populated resource field must match the requested filter; `experience_level=any` matches any requested experience, while blank/unknown resource values do not match a specific filter.
4. **Internship endpoint:** `/api/internships` forwards merged preferences. `get_internship_resources` applies `experience_filter` and `work_mode_filter`. Although `employment_type` is stored on resources, `apply_internship_filters` has no employment-type parameter, so the `apprenticeship` values on candidate rows 46–47 do **not** filter internship results.
5. **General routed/recommendation endpoints:** `/api/recommend` fetches all database resources and runs ranking; it does not call the job/internship strict filters. `/api/route` passes `user_query.preferences` to `route_query`; it does not merge the top-level typed filter fields before routing. Thus typed fields do not consistently work across API endpoints.
6. **Frontend:** `buildSupportRequest()` sends `message`, `category`, `preferences`, and `language`, and `fetchRecommendations()` posts to `/api/recommend`. The job question answers are preference labels such as “Student or fresher”; internship answers include “Beginner” and “On-site”. The frontend does not send `experience_filter`, `work_mode_filter`, or `employment_type_filter`. Its current flow therefore does not invoke the category endpoint’s strict metadata filters. User answers may contribute to general preference text ranking, which is distinct from verified eligibility filtering.
7. **Blank values:** The loader converts blanks to `None`. With no active filter, all resources are returned. With an active filter, a blank resource value is excluded. This avoids treating unknown as a match, but can omit useful resources when metadata is absent or inaccurate.
8. **Naming/normalization:** Stored resource vocabulary is lowercase snake_case. Filter utilities normalize query-side aliases, such as “on-site” to `on_site` and “internship” to `apprenticeship`; this does not validate stored values. The frontend question answers are not transformed into these typed filter fields.

## Recommended corrections — not applied

- **Do not treat vocabulary validity as source verification.** Keep all six populated values marked for review; no candidate filter value is supported well enough by the cited source material to be accepted as a factual eligibility/work-condition assertion.
- **Clarify resource type before setting employment filters.** Rows 25, 27 and 28 describe guidance/training/livelihood programmes rather than clearly defined vacancies. Consider whether employment filters apply to these service records at all. Do not change or remove their values until an authorized source review decides.
- **Verify opportunity attributes against exact programme notices.** For rows 26 and 46, verify experience, delivery mode and the appropriate classification (job training, internship or apprenticeship) from the current Pune/Maharashtra scheme terms. For rows 27 and 47, locate exact SARTHI programme evidence and confirm target-group restrictions, course format and whether there is an actual internship/job opportunity.
- **Verify service claims and data provenance first.** Row 28’s existing PMC link was inaccessible in the Stage 1 check. Do not use `self_employment` as an established programme attribute until official DAY-NULM/PMC evidence is located.
- **Keep eligibility separate from user preference.** `experience_level` currently behaves like a resource-side match label, but its model comment says “required” while several descriptions describe general programmes. Establish a clear meaning (for example, required experience versus experience group served) before treating it as eligibility.
- **Make filter wiring consistent only in a separately approved implementation stage.** Current frontend requests use `/recommend`, while strict filtering exists on category endpoints; typed values also fail to propagate through `/route`, and internship employment type is ignored. Decide the intended UI and endpoint contract, then test it without inferring rules from question answers.
- **Preserve unknowns.** If source records do not explicitly establish a filter attribute, store it as blank/unknown in a future approved data revision instead of guessing a value. This review does not alter the candidate.

## Final status: **Insufficient evidence**

The structural mapping is consistent and all 18 populated values match their respective model vocabularies. However, record-level provenance is incomplete, and the Stage 1 report does not support the filter meanings for these six records. Several are service/training programmes rather than clearly defined job listings, and the current user-facing request path does not apply the strict filters consistently. Do not promote these fields as verified eligibility or opportunity conditions without source confirmation and explicit approval.
