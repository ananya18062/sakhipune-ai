## Evidence tiers and limitations

1. **Direct primary evidence (this audit):** pages retrieved from the official government or provider URLs listed in the source register below. Each resource row identifies only the claims those pages actually support.
2. **Prior primary-source observations:** evidence transcribed in the Stage 1 provenance report, including earlier fetch results. It is identified as prior evidence where the current fetch did not reproduce it.
3. **Secondary evidence:** no secondary-source page was used to substantiate a resource claim in this audit.
4. **Not established:** no suitable source was present/retrieved, or the page was only a general landing page. A proposed source from Stage 1 is a place to investigate, not evidence that the claim is true.

The 18 direct fetch attempts included 3 transport/host failures (`legalservices.maharashtra.gov.in`, `pmc.gov.in`, `mavim.maharashtra.gov.in`). The two Pune District scheme pages redirected to canonical trailing-slash pages. Some returned content is sparse or a homepage, so it supports only what is explicitly stated. No live calls, emails, office visits, or current service-availability checks were made. Phone numbers, physical addresses, opening hours, fees, active enrollment, and the suitability of any resource for an individual were not independently tested.

## Application field purpose and evidence implications

- The ten candidate fields are `name`, `category`, `description`, `location`, `contact`, `language`, `keywords`, `experience_level`, `work_mode`, and `employment_type`. The repair diagnostics and mapping report confirm 46 repaired rows, 0 ambiguous rows, and a ten-column candidate; candidate row numbers are file positions, not database IDs.
- `SupportResource` in `backend/app/database/models.py` defines the three filter columns as nullable strings. Its constants document the accepted values, but SQLAlchemy does not enforce those sets or the semantic truth of stored values.
- `backend/load_resources.py` reads the candidate-shaped data using header keys, strips values, and maps blank filter cells to `None`; it does not validate filter meanings or source claims.
- `resource_normalizer.py` and `routes.py` carry those metadata values through normalized objects. The jobs filter compares active values; the internship filter only compares experience and work mode, not employment type.
- `/api/recommend`, used by `frontend/js/app.js`, ranks the complete resource set and does not apply these structured filters. The frontend posts preference answers rather than the typed filter properties. Consequently, the populated values are currently metadata, not a consistently user-facing, evidence-backed filter contract.
- Blank metadata is represented as unknown (`None`). A specific filter can exclude a resource with unknown metadata; the resource must not be assigned a value merely to avoid that exclusion.
